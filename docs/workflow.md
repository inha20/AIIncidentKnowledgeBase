# 팀 운영 워크플로

```
발견 ─► 등록(add) ─► 원인 분석 ─► 수정·검증 ─► 해결 기록(status) ─► 공유(report) ─► 정기 리뷰
```

## 1. 발견과 등록 (발견한 사람, 5분 이내)
- 오류를 본 즉시 `add` 로 등록합니다. 원인을 몰라도 됩니다(`root_cause` 기본값 "조사 중").
- **재현 가능한 정보**를 남깁니다: 모델명, 문제 프롬프트, 증상.
- 고객 정보·기밀은 마스킹합니다(예: `[고객명]`, `[금액]`).

## 2. 원인 분석 (담당자)
원인을 아래 순서로 점검합니다.
1. 맥락이 부족했나? (회사 정보·최신 정보 누락)
2. 지시가 모호하거나 충돌했나?
3. 출력 형식·길이 제약이 불명확했나?
4. 모델/도구의 한계인가? (그렇다면 프롬프트가 아닌 `mitigation` 으로 대응)

## 3. 수정과 검증
- `fixed_prompt` 를 만들고 **원래 실패한 입력**으로 다시 시험합니다.
- 비슷한 입력 2~3개로도 시험해 다른 곳이 깨지지 않는지 봅니다.
- 프롬프트로 부족하면 `mitigation` 에 사람 검수 단계, 규칙, 데이터 보강 등을 적습니다.

## 4. 해결 기록
```bash
promptsolution status INC-0007 resolved \
  --fixed-prompt "..." --mitigation "발송 전 사람 검수"
```
`resolved` 는 수정 내용이 없으면 거부됩니다.

## 5. 공유
- 주간: `promptsolution report -o reports/week-NN.md` 를 팀 채널에 공유
- 레코드는 Git 저장소로 관리해 Pull Request 로 리뷰하면 수정 프롬프트의 품질도 같이 검토됩니다.

## 6. 정기 리뷰 (월 1회, 30분)
- 반복되는 category/tag 를 찾아 **공통 프롬프트 가이드**로 승격
- `open` 중 high 이상 확인
- 분류 체계 조정

## 역할 제안
| 역할 | 책임 |
|---|---|
| 보고자 | 등록, 재현 정보 |
| 담당자 | 원인 분석, 수정 |
| 리뷰어 | 수정 검증, 해결 승인 |
| 운영자 | 리포트 공유, 월간 리뷰 |
